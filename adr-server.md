Сервер в данной модели является единственным источником правды. Он хранит в себе структкру файлов, папок.

Сервер реализует следующие интерфейсы:
1. Получить текущую версию
2. Скачать данные текущей версии. 
3. Протолкнуть обновление версии с клиента.

Подробно про 3.
Если последняя comitted версия у клиента совпадает с версией сервера, то тогда мы действительно атомарно блокируем эту функцию и начинаем выкачивание изменений. 
Это должно происходить атомарно. 
Если клиент падает мы получаем ошибку, то тогда сервер сохраняет текущую версию.
Пока же идёт процесс передачи мы скачиваем изменения не в активный корень, а в другую папку, чтобы не загрязнить данные корня. После этого мы начинаем процесс переноса данных, полученных с клиента в наш корень. Перед этим флаг, отвечающий за состояние ручки переводим в состояние с "uploading", в "updating". Если мы падаем на этом этапе (например сервер упал), то мы продолжаем выгрузку. Для этого мы постоянно пишем о том, какой файлик из копии был точно скачан. После успешного завершения передачи мы можем отдать клиенту информацию, что его версия стала закомиченной и он у себя локально тоже может сделать increase.

## Сессии загрузки

Состояние передачи не должно существовать только в памяти gRPC-соединения: при
разрыве соединения или перезапуске сервера его необходимо восстановить. Поэтому
для каждой начатой передачи сервер создаёт долговечную запись в таблице
`upload_sessions`. Байты файлов хранятся во временной staging-папке, например
`staging/<session_id>/`; таблица хранит состояние и метаданные операции.

Минимальная схема таблицы:

```text
upload_sessions
- id                 UUID, идентификатор сессии
- directory_id       UUID, синхронизируемая директория
- owner_id           идентификатор пользователя или клиента
- base_revision      версия директории, на которой начата сессия
- state              created | uploading | validating | committing |
                     committed | aborted | expired
- manifest_hash      хеш неизменяемого плана изменений (опционально)
- idempotency_key    ключ идемпотентности операции commit
- created_at
- updated_at
- expires_at         время, после которого незавершённая сессия очищается
- committed_revision NULL до успешного commit, иначе опубликованная версия
- error_code         NULL либо код последней ошибки
- error_message      NULL либо описание последней ошибки
```

Для файлов внутри сессии сервер хранит отдельные записи. Они образуют
неизменяемый manifest: до `commit` нельзя молча добавлять в сессию другие
файлы или менять их ожидаемые версии.

```text
upload_session_files
- session_id          UUID, ссылка на upload_sessions
- file_id             UUID, NULL для нового файла до его публикации
- path                относительный путь в директории
- operation           create | update | delete | rename
- expected_version    версия файла, на которой основано изменение
- content_hash        ожидаемый хеш содержимого, NULL для rename/delete
- size                ожидаемый размер, NULL для rename/delete
- staging_path        путь к временному файлу, NULL для rename/delete
- received_bytes      число принятых байтов
- state               pending | uploading | complete | failed
```

В первой версии отдельной таблицы `upload_chunks` нет. Сервер принимает чанки
каждого файла строго последовательно и сохраняет `received_bytes` в
`upload_session_files`. После разрыва соединения клиент возобновляет отправку
с этого смещения; если это окажется слишком сложно для первого клиента, файл
можно отправить заново. Поддержка произвольных диапазонов и докачки отдельных
пропущенных чанков будет добавлена позднее, когда появится практическая
необходимость.

При создании сессии сервер сохраняет её `base_revision`. Перед публикацией он
проверяет, что текущая версия директории ещё совместима с этой базовой версией,
а все данные в staging-папке полностью получены и прошли проверку целостности.

`commit` должен быть идемпотентным: если сервер уже перевёл сессию в
`committed` и записал `committed_revision`, повторный запрос с тем же
`idempotency_key` возвращает эту же версию и не создаёт новую. Это необходимо,
когда сервер успешно закоммитил изменения, но клиент не получил ответ из-за
разрыва сети.
